# パフォーマンスと最適化（Performance & Optimization）

## 1. 一言でいうと

**パフォーマンス最適化とは、利用者と事業の目標を満たすため、計測で特定したボトルネックへ最小の変更を加え、効果と副作用を再測定する活動です。**

「コードを速くする」ことだけではありません。P99を400ms以内にする、同じ費用で1,000 RPSを処理する、バッチを午前6時までに終える、という測定可能な目標が必要です。

## 2. なぜ必要なのか

遅い購入画面は離脱につながり、処理能力不足はセール時の失敗を招きます。しかし、推測でキャッシュや並列化を追加すると、整合性、メモリ、依存先負荷を悪化させます。

性能には複数の側面があります。

- **レイテンシ**: 1件が完了するまでの時間
- **スループット**: 単位時間に完了する件数
- **並行数**: 同時に系内に存在する仕事
- **飽和**: CPU、接続、キューなどが容量へ近づいた状態
- **効率**: 1件を処理する費用や資源量

## 3. 仕組み

### 4.1 分布で見る

P50は半数がそれ以下、P95は95%、P99は99%がそれ以下で完了する値です。P99は「最も遅い1%の最大値」ではなく、99パーセンタイルです。平均が同じでも長い裾を持つ分布では、一部利用者の体験が大きく異なります。

異なる時間窓・エンドポイント・地域を混ぜたパーセンタイルは解釈しにくいため、条件とサンプル数を明示します。

### 4.2 待ちと処理能力

安定した系ではリトルの法則 `L = λW` が、平均並行数 `L`、平均到着率 `λ`、平均滞在時間 `W` の関係を表します。たとえば500件/秒で平均0.2秒なら、平均約100件が系内にいます。これは原因を特定する式ではなく、容量と測定値の整合性を確認する道具です。

### 4.3 ボトルネックを特定する

```mermaid
flowchart LR
    Goal[性能目標] --> Baseline[同条件で基準測定]
    Baseline --> Profile[trace・DB plan・profile]
    Profile --> Change[一つの仮説を改善]
    Change --> Compare[再測定して比較]
    Compare --> Goal
```

CPU profileはCPU時間を使う箇所、heap profileはメモリ割り当て、traceはサービス間待ち、DBの `EXPLAIN` は実行計画を調べます。一つの道具だけで原因を決めません。

## 4. 具体例：商品一覧のN+1クエリ

商品100件を取得後、各商品の在庫を個別取得すると101回のDB往復が発生します。

```sql
-- 前提: 表示する商品IDが p1, p2, p3 と分かっている
-- 入力: 3つの商品ID
-- 期待結果: 在庫を1回の問い合わせで取得する
SELECT product_id, available_quantity
FROM inventory
WHERE product_id IN (:p1, :p2, :p3);
```

ORMのeager loadingやDataLoaderでも同じ考え方を実装できます。ただし、巨大な `IN`、不要な列を含むJOIN、メモリ上の過大な結果集合は新しい問題になります。ページサイズを制限し、実行計画、DB往復数、転送量、全体レイテンシを変更前後で比較します。

PostgreSQLの `EXPLAIN ANALYZE` は実際に文を実行します。更新文へ使う場合はデータ変更が起きるため、検証環境またはトランザクション内のロールバックなど安全策が必要です。

## 5. いつ使うか・使わないか

最適化は、SLO違反、容量不足、費用増加、負荷試験で明確なリスクが見つかったときに行います。データ量とアクセスパターンが本番に近い条件で測ります。

根拠なく低水準の実装へ置き換えたり、読みやすさを犠牲にしたりしません。起動時に一度だけ実行する処理を数マイクロ秒短縮しても利用者価値はほぼありません。まず最も時間または費用を占める経路を選びます。

## 6. 設計上の選択肢とトレードオフ

| 最適化 | 期待効果 | 代償 |
|---|---|---|
| キャッシュ | 読み取り遅延とDB負荷を削減 | 古い値、失効、メモリ |
| バッチ化 | 往復・固定費を削減 | 待ち時間、巨大リクエスト |
| 並列化 | 独立処理の経過時間を短縮 | CPU・依存先負荷、順序制御 |
| 接続プール | 接続確立費用を削減 | 過大設定でDBを圧迫 |
| インデックス | 対象検索を高速化 | 書込・容量・保守コスト |
| 非同期化 | 利用者の待ち時間を短縮 | 完了通知、再試行、整合性 |

レイテンシとスループットは常に反対ではありません。バッチ化はスループットを上げながら、バッチ待ちで個別レイテンシを増やす場合があります。実装と負荷条件ごとに測ります。

## 7. よくある失敗と運用上の注意

### 平均だけで合格にする

P50、P95、P99、最大、エラー率、サンプル数を併記し、利用者層やAPI別に見る必要があります。

### 負荷生成器が先に限界へ達する

クライアント側CPU、接続、帯域を監視します。要求レート、同時数、データ分布、think timeを記録します。

### キャッシュが温まった結果だけを使う

コールドスタート、失効直後、人気キー、キャッシュ障害も試します。

### プロファイラを無防備に公開する

診断エンドポイントは内部ネットワークと認証で保護します。収集自体のオーバーヘッドを測り、一度に必要なprofileだけ取ります。

### 変更をまとめて比較する

複数変更を同時に入れると効果と回帰の原因が分かりません。同一条件で一つずつ比較し、性能テストを継続実行します。

## 8. 第三者へ説明する

### 30秒で説明するなら

> パフォーマンス最適化は、目標を数値化し、実測したボトルネックだけを改善して再測定する活動です。平均だけでなくP95やP99、エラー率、飽和を見ます。trace、DB実行計画、CPU・メモリprofileを使い分け、速度と整合性、費用、保守性のトレードオフを確認します。

### 3分で説明するなら

1. P99や処理可能RPSなど利用者・事業の目標を決める。
2. 本番に近い負荷とデータで基準値を測る。
3. trace、profile、実行計画で支配的な待ちや処理を特定する。
4. N+1をバッチ取得に変えるなど、一つの仮説を実装する。
5. 同条件で効果、エラー、資源、費用を比較し、回帰テストへ残す。

## 9. ケース問題・追加質問

### ケース問題

商品一覧の平均は100msですが、P99は3秒です。最初に何を調べますか。

::: details 模範回答
時間帯、ページサイズ、キャッシュヒット、商品数、地域、DB query数で遅い要求を分けます。遅いtraceからDB、外部API、キュー待ちのどこが支配的か確認し、該当時刻の実行計画やロックを調べます。平均だけを目標にせず、P99のSLOとサンプル数を定義して変更前後を比較します。
:::

### よくある追加質問

**Q. インデックスを追加すれば必ず速くなりますか？**

いいえ。選択性、表サイズ、実行計画によります。書き込みと保存容量も増えるため `EXPLAIN` と実測で確認します。

**Q. 並列化すればレイテンシは下がりますか？**

独立処理なら下がる可能性がありますが、共有CPUや依存先を飽和させると悪化します。同時数を制限します。

**Q. 本番でprofileを取れますか？**

代表的な負荷を得やすい一方、収集にはオーバーヘッドがあります。アクセスを制限し、短時間・一種類ずつ測定します。

## 10. まとめ

- 性能目標はレイテンシ、スループット、エラー、費用で数値化する。
- 平均だけでなく分布と飽和を見る。
- 計測、原因仮説、最小変更、再測定の順で進める。
- N+1、キャッシュ、バッチ、並列化には新しい代償がある。
- 現実的な負荷条件を固定し、性能回帰を継続検出する。
