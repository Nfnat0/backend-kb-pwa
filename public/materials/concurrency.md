# 並行処理（Concurrency）

## 1. 一言でいうと

**並行処理とは、複数の仕事を時間的に重ねて進める構造であり、共有状態と終了条件を明示して安全性と応答性を保つ設計です。**

並行性（Concurrency）は複数の仕事を進行中にする構造、並列性（Parallelism）は実際に同時実行することです。1コアのイベントループにも並行性はありますが、CPU処理を同時に進めるには複数コアやプロセスが必要です。

## 2. なぜ必要なのか

ECサイトのAPIは、DB、決済、配送APIの応答を待ちます。待っている間に別リクエストを処理すれば資源を活用できます。しかし無制限に処理を増やすと、DB接続枯渇、メモリ増大、タイムアウトの連鎖が起きます。さらに共有データを同期せず更新すると、結果が実行順序に依存します。

したがって並行処理は「速くする技法」だけでなく、並行数、共有範囲、キャンセル、タイムアウトを設計する問題です。

## 3. 仕組み

### 4.1 実行モデル

| モデル | 特徴 | 向く処理 | 注意点 |
|---|---|---|---|
| プロセス | アドレス空間を分離 | 障害分離、CPU処理 | 通信と生成コスト |
| OSスレッド | 同一プロセスのメモリを共有 | 同期I/O、CPU処理 | 共有状態、切替コスト |
| 軽量タスク/コルーチン | ランタイムが多数を管理 | 多数のI/O待ち | ブロッキング処理、リーク |
| イベントループ | 少数スレッドで準備完了I/Oを処理 | 高接続数のネットワークI/O | CPU処理がループを塞ぐ |

`epoll`や`kqueue`は、すべての接続を順番に確認せず、準備ができたI/OをOSから通知してもらう仕組みです。非同期I/Oそのものが処理時間を消すわけではなく、待ち時間を別の仕事へ使います。

### 4.2 データ競合と同期

データ競合は、同じメモリへ複数の実行単位が同期なしでアクセスし、少なくとも一つが書き込みである状態です。結果の誤りだけでなく、言語のメモリモデル上未定義・予測困難な動作になる場合があります。

```mermaid
flowchart LR
    R1[処理A: 在庫10を読む] --> W1[9を書き込む]
    R2[処理B: 在庫10を読む] --> W2[9を書き込む]
    W1 --> Lost[2件購入したのに在庫9<br/>更新消失]
    W2 --> Lost
```

主な手段は、ロック、アトミック操作、メッセージ受け渡し、DBの制約・トランザクション、状態を共有しない設計です。アトミックなカウンタだけでは、複数項目にまたがる業務不変条件は守れません。

## 4. 具体例：注文情報を並行取得する

注文詳細、配送予定、決済状態を独立に取得し、キャンセルと上限を共有するGoの最小例です。

```go
// 前提: 3つの取得は互いに依存せず、各関数はctxのキャンセルを処理する。
ctx, cancel := context.WithTimeout(r.Context(), 800*time.Millisecond)
defer cancel()

g, ctx := errgroup.WithContext(ctx)
g.SetLimit(3)

g.Go(func() error { return loadOrder(ctx, orderID) })
g.Go(func() error { return loadDelivery(ctx, orderID) })
g.Go(func() error { return loadPayment(ctx, orderID) })

if err := g.Wait(); err != nil {
    // 期待結果: 一つが失敗・期限超過なら残りも停止を要求される。
    return err
}
```

独立処理の逐次実行が各200msなら約600msですが、並行実行の理想値は最長の約200msです。実際は接続プール、下流の容量、スケジューリングに左右されます。並行化前後を計測します。

## 5. いつ使うか・使わないか

### 並行化が向く場合

- 独立した複数のI/O待ちを重ねられる
- キューの仕事を上限付きで複数ワーカーへ配れる
- CPU処理を分割でき、複数コアを使う価値がある

### 避ける・後回しにする場合

- 処理が極端に短く、調整コストの方が大きい
- 実行順序が業務上重要で、並行化の利点が小さい
- 下流サービスやDB接続がすでに上限に近い
- 正しさ、キャンセル、エラー回収を説明できない

## 6. 設計上の選択肢とトレードオフ

| 判断 | 利点 | 代償 |
|---|---|---|
| 共有状態＋ロック | 既存構造へ適用しやすい | 競合、デッドロック、待ち時間 |
| メッセージ受け渡し | 所有権を明確にしやすい | キュー詰まり、終了制御 |
| 楽観的競合制御 | 競合が少ないと効率的 | 衝突時の再試行が必要 |
| ワーカープール | 資源使用を制限できる | 上限が低いと待ち、高いと下流を圧迫 |

並行数は式だけで固定せず、CPU利用率、DB接続数、下流のレート制限、p95/p99遅延、キュー待ち時間を見て調整します。

## 7. よくある失敗と運用上の注意

### タスクを開始して回収しない

送信先のないチャネル、期限のないI/O、読み手を失ったキューはタスクを残します。親のキャンセルを伝播し、誰が終了を待つかを決めます。

### ロックの範囲が広い・順序が不統一

ロック中に外部I/Oを行うと待ちが長くなります。複数ロックは取得順を統一し、可能なら共有状態を小さくします。タイムアウトだけでは壊れた不変条件を修復できません。

### レース検出器だけで安全だと思う

動的なレース検出器は実行された経路しか検査しません。CIで負荷・統合テストにも使い、設計レビューと不変条件のテストを併用します。

### 監視する

実行中タスク数、キュー待ち、接続プール待ち、タイムアウト、デッドロックの兆候、CPU・メモリを監視します。デプロイ時は新規受付を止め、実行中処理へ期限付きで終了機会を与えます。

## 8. 第三者へ説明する

### 30秒で説明するなら

> 並行処理は複数の仕事を時間的に重ねる構造で、並列処理は実際に同時実行することです。I/O待ちの多いAPIでは応答性を高められますが、共有状態の競合、処理リーク、下流の過負荷が増えます。そのため同期方法だけでなく、並行数、キャンセル、タイムアウト、終了待ちを一緒に設計します。

### 3分で説明するなら

1. 並行性と並列性を区別する。
2. スレッド、軽量タスク、イベントループの役割を説明する。
3. ECサイトの独立した外部I/Oを並行取得する例を示す。
4. データ競合、デッドロック、リーク、下流過負荷を挙げる。
5. 上限、所有権、キャンセル、観測を設計すると結ぶ。

## 9. ケース問題・追加質問

### ケース問題

セール時に注文APIを高速化するため、在庫確認を1,000並行にしました。APIは一時的に速くなりましたがDB接続が枯渇しました。どう直しますか。

::: details 模範回答
API単体の速度ではなくDBを含む容量を基準にします。接続プールより小さい並行上限を設け、キュー待ちとタイムアウトを明示します。負荷試験でDBのCPU、ロック待ち、接続待ち、p99を測り、許容できる上限を決めます。必要なら在庫処理の競合単位やDBクエリも改善します。
:::

### よくある追加質問

**Q. 非同期にすれば必ず速くなりますか？**

いいえ。I/O待ちを重ねられる場合に有効です。CPU時間や下流容量は増えず、調整コストが追加されます。

**Q. Mutexとチャネルはどちらがよいですか？**

小さな共有状態を保護するならMutexが単純です。仕事や所有権を受け渡すならチャネルが自然です。言語の流行ではなく不変条件から選びます。

## 10. まとめ

- 並行性は構造、並列性は同時実行である。
- I/O待ちを重ねられるが、下流の容量は増えない。
- 共有状態を減らし、必要な同期で不変条件を守る。
- 並行数、キャンセル、終了待ちまで設計する。
- レース検出と本番指標の両方で検証する。
