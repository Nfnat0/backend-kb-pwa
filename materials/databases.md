# データベース（Databases: SQL / NoSQL）

## 1. 一言でいうと

**データベース設計とは、保存する事実、その関係と制約、主要な読み書き方法を明確にし、正しさ・性能・運用の優先順位に合う仕組みを選ぶことです。**

「SQLかNoSQLか」は製品名の比較ではありません。注文と明細を同時に確定したい、商品IDで高速に引きたい、イベントを大量に追記したい、といったアクセスパターンと整合性要件から選びます。

## 2. なぜ必要なのか

データはアプリを再起動しても残り、複数の処理から同時に変更されます。設計を誤ると次が起きます。

- 注文はあるのに明細がない不完全な状態が残る
- アプリの不具合で同じ注文番号が二つ作られる
- 一覧が遅くなり、根拠なくインデックスを増やして書き込みも遅くなる
- レプリカの遅延で、更新直後の値が見えない
- 分離レベルを理解せず、在庫や残高の競合を見逃す

正しさはアプリコードだけで守らず、型、NOT NULL、外部キー、一意制約、トランザクションといったDBの機能でも守ります。

## 3. 仕組み

### 4.1 データモデルを選ぶ

| 種類 | 得意なモデル | 向く例 | 確認すること |
|---|---|---|---|
| リレーショナルDB | 表、関係、制約、JOIN | 注文、決済、会員 | トランザクション境界とスキーマ変更 |
| Key-Value | キーから値を取得 | セッション、単純な状態 | キー以外の検索、値の整合性 |
| ドキュメントDB | 自己完結した階層データ | 商品カタログ、CMS | 重複データの更新と問い合わせ |
| Wide-column / 時系列 | 定めたキーで大量追記・集約 | 操作ログ、計測値 | 先にアクセスパターンを固定できるか |

製品は複数の特徴を持ちます。Redisを永続データに使う、PostgreSQLでJSONを使うなども可能なので、「NoSQLは整合性が弱い」と一括りにせず、製品と設定の保証を確認します。

### 4.2 インデックス

インデックスは、列の値から行の位置を探す補助構造です。B-treeは等価検索と範囲検索に広く使われます。ただし、計算量を単純に `O(log N)` と断定しても実際の速さは分かりません。選択度、キャッシュ、行取得、並び替え、統計情報などが影響します。

複合インデックス `(user_id, created_at DESC, id DESC)` は、利用者ごとの注文を新しい順に読む問い合わせと相性がよい一方、`created_at` だけの検索に同じように効くとは限りません。実行計画で確認します。

### 4.3 トランザクションと分離レベル

トランザクションは複数操作を一つの単位として成功または失敗させます。分離レベルは、並行処理の途中で何が見えるかを決めます。

| PostgreSQLのレベル | スナップショット | 起こり得ること |
|---|---|---|
| Read Committed | 文ごと | 同じトランザクション内の再読で値が変わり得る |
| Repeatable Read | トランザクション基準 | 読みは安定するが、直列化できない更新競合は残り得る |
| Serializable | 直列実行と同等の結果を目指す | 競合時に一方が失敗し、全トランザクション再試行が必要 |

PostgreSQLでは `Read Uncommitted` を指定しても `Read Committed` として扱われ、Repeatable Readでもファントムリードは発生しません。分離レベルの実装はDB製品ごとに確認します。

## 4. 具体例：注文と明細を保存する

前提は `users` と `products` が存在し、入力は利用者IDと商品・数量、期待結果は注文と明細が両方保存されるか、どちらも保存されないことです。

```sql
BEGIN;

INSERT INTO orders (id, user_id, status, total_amount)
VALUES ('ord_42', 7, 'PENDING', 3000);

INSERT INTO order_items (order_id, product_id, quantity, unit_price)
VALUES ('ord_42', 101, 2, 1500);

COMMIT;
```

`orders.id` の主キー、`order_items.order_id` の外部キー、数量のCHECK制約をDBにも持たせます。クエリが遅い場合は推測でインデックスを足さず、次のように実測します。

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, total_amount
FROM orders
WHERE user_id = 7
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

`ANALYZE` は実際に文を実行するため、更新文や本番負荷では注意します。推定行数と実行行数、走査方法、読み取ったバッファ、並び替えを見ます。

## 5. いつ使うか・使わないか

- 関係、制約、複数行のトランザクションが中心ならRDBを第一候補にする
- キーアクセスが明確で、規模や可用性要件がRDBの運用範囲を超えるなら専用ストアを検討する
- 柔軟なJSONを保存したいという理由だけで、関係と制約を捨てない
- キャッシュを唯一の正本にする場合は、永続性と復旧保証を明示する
- 一つのデータを複数DBへ無計画に二重書きしない

まず正本を一つ決め、検索インデックスやキャッシュなど派生データは再構築できる設計にすると責任が明確です。

## 6. 設計上の選択肢とトレードオフ

| 選択 | 得られるもの | 代償 |
|---|---|---|
| 正規化 | 重複更新を減らし制約を守りやすい | 読み取り時のJOINが増える |
| 非正規化 | 主要な読み取りを単純化できる | 同じ事実の同期が必要 |
| インデックス追加 | 対象問い合わせを高速化できる | 書き込み、容量、保守コストが増える |
| 読み取りレプリカ | 読み取り負荷を分散できる | 遅延、読み書き整合性、切替運用が増える |
| パーティション | 大きな表の保守や限定検索を改善できる | キー選択、跨る問い合わせ、再配置が複雑 |

レプリケーションはバックアップの代わりではありません。誤削除も複製されるため、別の保持方針と復元訓練が必要です。

## 7. よくある失敗と運用上の注意

### インデックスを多く作れば速いと考える

各インデックスはINSERT・UPDATE・DELETEで更新されます。実際の遅い問い合わせと利用頻度から追加し、未使用・重複インデックスを確認します。

### アプリの事前SELECTだけで競合を防ぐ

確認後からINSERTまでに別処理が割り込めます。一意制約や条件付きUPDATEなど、DBで原子的に判定し、競合エラーを扱います。

### コネクション数を増やし続ける

DBの同時処理能力を超える接続は待ちとメモリ消費を増やします。アプリ全体のプール合計、実行時間、ロック待ち、CPU・I/Oを観測します。

### バックアップを取るだけ

復元できるか、どの時点まで戻せるか、何分で再開できるかを定期的に試験します。スキーマ変更と復旧手順も合わせて管理します。

## 8. 第三者へ説明する

### 30秒で説明するなら

> データベースは、保存する事実と制約、主要なアクセス方法に合わせて選びます。注文のように関係とトランザクションが重要ならRDBが有力です。インデックスは読み取りを助ける代わりに書き込みコストを増やし、レプリカやパーティションは規模へ対応する代わりに整合性と運用を複雑にします。

### 3分で説明するなら

1. データモデル、アクセスパターン、整合性が選定軸だと定義する。
2. 注文と明細をRDBの制約とトランザクションで守る例を示す。
3. インデックスは問い合わせに合わせ、実行計画で確認すると説明する。
4. 分離レベルごとに並行処理の見え方が違うと示す。
5. レプリカ、パーティション、NoSQLには新しい整合性・運用コストがあると結ぶ。

## 9. ケース問題・追加質問

### ケース問題

「在庫が1以上なら1減らす」を、同時注文でも売り越さないよう実装してください。

::: details 模範回答
事前にSELECTしてから別のUPDATEを行うだけでは競合します。たとえば `UPDATE inventory SET quantity = quantity - 1 WHERE product_id = 101 AND quantity >= 1 RETURNING quantity` のように条件判定と更新を一文で行い、更新行が0なら在庫切れとします。注文保存との原子性が必要なら同じトランザクションに入れます。複数DBへ跨るなら予約状態や補償処理を別途設計します。
:::

### よくある追加質問

**Q. NoSQLはSQLより速いですか？**

一概には言えません。限定したアクセスパターンへ最適化しやすい製品はありますが、データ量、問い合わせ、整合性、構成で結果は変わります。

**Q. Serializableならロックを考えなくてよいですか？**

正しさを得やすくなりますが、競合時の直列化失敗を想定し、トランザクション全体を安全に再試行する必要があります。

## 10. まとめ

- DBはデータの関係、制約、アクセスパターンから選ぶ。
- 正しさを型、制約、トランザクションでも守る。
- インデックスは実際の問い合わせと実行計画から設計する。
- 分離レベルと製品ごとの保証を区別する。
- レプリカ、パーティション、専用ストアは運用上の代償も含めて採用する。
